NiCoNiCode
本项目是一个web应用，主要提供以下服务：
- 一个可对话的ai agent，其提供关于开源项目/热点技术的问答（举例：用户询问springboot是什么，有什么亮点，然后ai基于我们的知识库进行问答）（同时提供对用户上传的github相关链接进行分析了解接着总结等等功能（比如用户提供一个github仓库链接，ai给予分析总结））
- 一个对计算机领域的前沿技术/热点技术（比如说在上面的ai对话中被各个用户提到或询问的次数超过一定阈值，定义其为热点技术或者通用技术）进行追踪的ai agent（“狗仔“），其负责 管理并维护前沿/通用/热点项目/技术的名单，对这些项目/技术/中间件等进行追踪（每间隔一段时间，通过rss/官方新版本发行/github官方仓库/官方文档/官方页面变化（sitemap.xml）等多方面进行新版本的检测），接着根据更新内容总结编写出一份报道，展示在页面中，同时存入我们的知识库
- 一个完整的知识库体系，其中存储 产生于上面的ai对话中的技术点或者对某个热点技术/开源项目的分析与总结（举例：用户询问springboot是什么，有什么亮点，此时我们的ai进行总结并回复，这个总结的内容在经过我们的后处理之后作为文档存入我们的知识库）以及 上面“狗仔“agent的报道内容

关于我们最终呈现的web，主要有以下四个页面：
一个首页，后续考虑存放什么内容
一个ai agent的对话页面（参考deepseek的浏览器中的网页形式）
一个“狗仔“agent生成/我们管理员人为编写的报道的展示页面
一个知识库所有文档的展示页面

关于技术选型：
前端：任意，只要能达到效果即可
后端：Spring Boot + LangChain4j + MyBatis-Plus
数据库： mysql + qdrant
可以使用docker部署中间件或其他服务（比如mcp server）

关于页面要求：
干净清爽简洁，我们的web基本是纯文字的

关于ai agent的设计：
- 使用mcp对数据源以及tool进行封装，统一agent的调用能力
- 预回答的设计，通过用户问题以及预设问题的相似度匹配，提供预回答给ai，通过预回答增强ai返回内容的有效性，或使用属性意图分类体系进行意图识别与歧义引导
- 对繁杂的问题进行重写与拆分
- 使用RAG丰富ai的上下文，增强答案的针对性
- 使用ReAct模式，提高ai的思维链逻辑性
- 会话记忆：滑动窗口 + 自动摘要压缩，控制Token成本的同时保留关键上下文
- 多路检索引擎，意图定向 + 全局向量双通道并行，检索结果经去重，重排序等后处理流水线
- 多agent协作，在面对复杂任务，可能需要处理3个以上领域的工作时，通过agent调用子agent进行不同领域的任务分发以及结果汇总，进行任务的完成（可用于“狗仔“agent）

关于一些杂项：
- 由于我们服务器在国内，无法直接访问github，可以通过现有的一个cloudflare的worker进行github这边的流量中转
- ai模型使用openAI的标准，目前使用的是deepseek-v3
- 用户注册之后才能提供与ai对话的功能，通过邮箱发送验证码进行注册，暂且使用spring自带的SMTP服务以及qq邮箱进行验证码发送

==================================

关于对话agent的整体链路设计：

首先整个链路中都要通过traceID进行全链路追踪

优化之前的硬编码+logback方案，优化为：
在请求入口生成Trace ID：通过一个过滤器（Filter）或拦截器（Interceptor）为每个请求生成一个唯一的Trace ID，并将其存入MDC（MDC.put("traceId", traceId)）。
利用AOP拦截关键方法：使用Spring AOP编写切面，在方法执行前后打印日志（如入参、出参、耗时），日志中自动包含MDC中的Trace ID。
确保异步线程传递Trace ID：如果使用了线程池（如@Async），需要将MDC上下文传递到子线程。
日志配置：在logback-spring.xml的pattern中添加%X{traceId}以输出Trace ID。
这样，整个调用链路中的所有日志都会自动带上同一个Trace ID，便于串联分析。

然后优化每一个链路节点
首先是用户发送消息，到后端进行的第一部操作 - 意图识别 + 重写

意图识别这里采用三级级联策略（规则->向量->LLM） + 树形意图分支（主意图 + 子意图）
L0噪音过滤
L1规则，纯正则/关键词匹配，高精度场景快速返回
L2向量相似度，内存方案，在内存中预先存储一些已经写定的样本进行相似度比对
L3LLM兜底
从L1到L3，失效依次降级，L1 + L2结果一致，直接返回结果，否则进入L3兜底，L3失败，使用L1/L2最高置信度结果，全部失败则返回一个general的结果
（
  L0 噪音过滤 → NOISE_SKIP
  L1 规则 conf≥0.85 → 直接返回
  L2 向量 conf≥0.80 → 返回（合并L1槽位）
  L1+L2 一致 → +0.10增信 conf≥0.75 → 返回
  L3 LLM 兜底（带 hint）→ 返回
  L3 失败 → 降级 L1/L2 最佳 → 全失败 → GENERAL_CHAT(0.3)
）

关于用户query重写以及分task，采用以下设计

重写策略——两级级联         
                                                                                                                                                                                                                                                               Fast Path: 规则化重写（<1ms）                                                                                                                                                                                                                                                                 触发条件：意图分类来自 L1 且 confidence ≥ 0.85 且消息无指代词（它/这个/那个/前面/上面）且为单一问题                                                                                                                                                                                           
处理方式：                                                                                                                                                                                                                                                                                    
- 直接使用意图分类的 slots 填充查询模板                                                                                                                                                                                                                                                       
- 例：Intent=TECH_QUERY/CONFIGURATION, slots={techName: "Spring Boot"} → "Spring Boot 配置方法"                                                                                                                                                                                               
- 返回单个 SubTask，strategy = RULE_TEMPLATE        
                                                                                                                                                                                                                                          
Slow Path: LLM 重写 + DAG 拆分（200-500ms）                                                                                                                                                                                                                                                   
触发条件：不满足 Fast Path 的所有消息                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    
增强 prompt：                                                                                                                                                                                                                                                                                 
- 输入意图分类结果（intent/subIntent/slots）作为 hint                                                                                                                                                                                                                                         
- 要求输出 DAG 结构：每个子任务带 id、query、type、dependsOn                                                                                                                                                                                                                                  
 - LLM 需判断子任务间的依赖关系 

关于DAG设计，DAG执行引擎

1. 从 SubTask 列表构建邻接表                                                                                                                                                                                                                                                                  2. 计算入度，找出所有根节点（入度=0）                                                                                                                                                                                                                                                         3. 按波次执行：                                                                                                                                                                                                                                                                               
- Wave N：所有入度=0 的节点并行启动（CompletableFuture）                                                                                                                                                                                                                                    
- 每个节点：调用 ragService.retrieveContext(task.query, task.intent.name())                                                                                                                                                                                                                 
- 节点完成后：更新后继节点入度，新的入度=0 节点进入下一波                                                                                                                                                                                                                                   
4. 有依赖的节点可访问前驱节点的 ragContext 作为补充上下文                                                                                                                                                                                                                                     
5. 全部完成后：合并所有 SubTask 的 ragContext 为统一上下文     

接下来看到上下文管理和记忆管理

记忆管理的设计大致如下：
使用LangGraph，通过图+状态的流转实现双层记忆，一层为用户级记忆，一层为会话层记忆，并且做好记忆隔离，避免同一用户的不同会话中出现记忆污染

接下来看到ReAct过程中的RAG/tool调用（关于缓存，可以引入Redis作为内存数据库）

对RAG大概要做以下优化：
- 不是每一步都需要检索。可以让 LLM 在 Thought 中明确判断是否需要外部知识，或由意图识别层预先标记。这样可以避免不必要的检索
-  缓存检索结果
	相同查询缓存：对完全相同的查询（或经过归一化）缓存检索结果，适用于高频问题。
	相似查询缓存：使用 embedding 近似，对相似度超过阈值的结果直接返回缓存。
	使用 Redis 等内存缓存，设置合适的过期时间
- 检索结果重排（Rerank）
	初次检索返回 top-k（如 20 个）候选，再用轻量级重排模型（如 cross-encoder）选出最相关的 3-5 个，提升准确率，同时避免将过多无关信息喂给 LLM
- 同时从向量库、关键词索引（如 BM25）、结构化数据库检索，合并结果后去重排序，提高召回率。可并行执行各路检索，不增加总延迟

对tool调用大概要做以下优化：
- 并行工具调用
	当 LLM 在一次 Thought 中决定调用多个独立工具时，可以并行执行它们（例如同时查天气和新闻）。需要在 prompt 中鼓励模型输出并行调用，并在执行时用异步方式并发
- 工具调用缓存
	对于幂等的工具（如获取当前时间、查询固定数据），缓存结果并设置过期时间，避免重复调用、
- 工具调用的结果摘要
	工具返回结果可能很大（如长文本、大量数据），在喂给 LLM 之前进行摘要或截断，避免 token 爆炸

对ReAct本身大概要做以下优化：
- Plan-and-Execute 替代多次 ReAct 循环
	对于步骤明确的任务，先用一次 LLM 调用生成完整计划（Plan），然后依次执行工具，最后再调用一次 LLM 生成最终答案。相比 ReAct 的多轮 Thought-Action 循环，可大幅减少 LLM 调用
- 批量工具调用
	在一次 Thought 中让 LLM 输出多个工具调用（并行或串行），然后一次性执行，将结果合并后再给 LLM 一次生成答案。减少多次交互
- 单步工具调用直接生成答案
	对于简单的单工具任务（如“查一下北京的天气”），可以直接使用 Function Calling 获取工具结果，然后一次性生成答案，无需循环

关于结合记忆管理/上下文管理的优化：
- 利用长期记忆预填充检索
	用户级记忆中可能保存了用户的偏好、之前检索过的知识等，可以在检索前先用这些信息作为查询的补充（例如改写查询），提高检索相关性
- 利用会话记忆避免重复检索
	如果同一会话中用户问了相似问题，可以从会话记忆中直接返回之前检索过的内容，避免重复检索。会话记忆中的历史 RAG 结果可以缓存
- 记忆驱动的检索时机
	根据用户级记忆（如用户对某领域感兴趣），在开始 ReAct 前主动预检索该领域的最新信息，作为候选上下文，减少后续检索次数
